Contributing

Netherrack is built from scratch, experimental, and still early — there’s a lot of room to help. This page summarizes the project’s own CONTRIBUTING.md; read that file for the complete, current version.

Before you start

  • Read the README.
  • Check existing issues and pull requests, so you’re not duplicating work already in progress.
  • For anything large, open an issue first to talk through the approach.

Netherrack is still evolving quickly — internal systems and structure may change without notice.

Development setup

You’ll need a JDK, Apache Maven, and Git. A Linux environment is recommended for testing, though contributions shouldn’t be unnecessarily Linux-specific.

git clone https://github.com/NetherrackOSS/Netherrack.git
cd Netherrack
bash mvnw clean package

The JAR lands in target/.

Testing your changes

What to test depends on what you touched, but commonly includes:

  • Starting and stopping the server.
  • Console commands and server.properties.
  • Connecting with an actual Bedrock client — strongly encouraged for anything networking- or protocol-related.
  • Block interactions and world-related functionality.
  • That nothing that worked before has regressed.

If a change can’t be tested yet because the relevant system doesn’t exist, say so in the pull request.

Where help is welcome

Protocol & networking

Bedrock protocol implementation, NetherNet integration, login and play handling.

World & blocks

World and chunk systems, block systems, persistent world storage.

Gameplay & plugins

Entity systems, plugin API improvements, and new player or world features.

Everything else

Server configuration, console commands, logging, performance, testing, documentation, bug fixes, developer tooling, Linux compatibility.

Got an idea that isn’t listed? Open an issue and discuss it.

Architecture

Netherrack is developed independently rather than as a clone of an existing server. Keep its architecture and long-term goals in mind, and avoid copying implementation code from other server software — inspiration and research are fine, but contributed code should be independently written and properly licensed. Netherrack uses open-source CloudburstMC components for networking and the Bedrock protocol; respect their licenses too.

Code style

Keep code readable, simple, consistent with what’s around it, properly named, and focused on one responsibility where practical. Avoid unnecessary abstraction. Comments should explain why, when that isn’t obvious from the code itself.

AI-assisted contributions

Allowed, but you’re responsible for what you submit: review the generated code, understand what it does, verify it builds and behaves correctly, check for copied or potentially copyrighted implementation details, and don’t submit large amounts of unreviewed generated code just because it compiles.

Reporting bugs

A good bug report includes:

  • What happened, and what you expected instead.
  • Steps to reproduce it.
  • Netherrack version or commit (/version gives you this).
  • Operating system, Java version, and Minecraft Bedrock Edition version.
  • Relevant console output or stack traces — the complete one, for crashes.

Open an issue

Feature requests

Welcome too. Explain what the feature would do, why it would be useful, how it might work, and whether it depends on something unfinished. Some features may be intentionally postponed while the underlying architecture is still being built.

Pull requests

  • Keep each PR focused on one change, or a closely related set of changes.
  • Explain what you changed, why, and how you tested it. Mention related issue numbers.
  • Avoid unrelated formatting or refactoring.
  • Make sure the project still builds.

PRs may be asked to change, simplified, or declined if they don’t fit the project’s current direction — especially for large architectural changes this early on.

Dependencies

Adding one? Explain why it’s needed, prefer established and actively maintained libraries, make sure its license is compatible with GPL-3.0, and avoid adding one for something reasonably implementable without it. Never copy third-party source into Netherrack without verifying its license permits that.
